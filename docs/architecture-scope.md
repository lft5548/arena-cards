# 架构与交付范围

Arena Cards 以模块边界、房间单写入、故障正确性和实测性能为设计主线。当前支持的实现、验证与边界见 [阶段交付](phase-delivery.md) 和 [支持范围](project-status.md)。

## 功能域

| 功能域 | 当前实现 | 适用边界 |
| --- | --- | --- |
| 模块 | gateway/app/match/room/battle/persistence/ranking/metrics | 网络不直接修改战斗，匹配不负责结算 |
| 房间执行 | FIFO RoomCommand、单 actor、计时与异步完成回投 | 每房间一个线程，队列与共享服务仍有同步 |
| 规则与回放 | 九张代表卡牌、版本化事件/快照、离线完整重建 | 固定槽位和确定性规则，摘要用于一致性诊断 |
| 协议 | 完整 TextV1/ProtoV1、混合房间、共用生成 schema | Protobuf 版本固定，显式关闭时仅 TextV1 |
| 权威存储 | MySQL 事务与幂等、有界连接池、断线退避 | API 串行保护，同数据库单实例锁 |
| 缓存 | Redis Lua、Outbox、连接与读写有界等待、原子重建 | Redis 非权威源，失败保留补偿记录 |
| 在线恢复 | full/tail、状态/RNG/token/ACK/绝对期限/pending result | 同库同规则单实例重启，无自动多实例接管 |
| 网络生命周期 | 准入、帧限流、心跳、背压和预算退出 | 每连接限制，关闭不能撤销已提交 SQL |
| Unity | UGUI 双客户端、权威状态展示、重连与排行榜 | 展示层只连接游戏服务，不访问数据库 |
| 性能与故障 | 20/100/200 Bot、分段持久化指标和有限故障窗口 | 本机条件实测，不作生产容量承诺 |
| 演示与证据 | 启动/检查入口、双客户端说明、证据导航与技术路径 | 彩排结果按演示报告记录 |

## 状态与线程边界

Gateway 处理 socket、帧和协议适配；应用层校验身份与业务路由；Matchmaker 负责配对；Room 拥有战斗与连接生命周期；Battle 不依赖 socket/SQL/UI。

状态修改统一进入 Room actor。Session writer 消费有界发送队列，MySQL 结算和回放 writer 使用不可变副本，完成后回投命令。慢客户端、存储故障和重连的影响在对应边界内处理。

## 数据与确认边界

MySQL 同一事务提交 match_results、积分和 pending Outbox。结算成功回投后交付 MatchResult，Redis 独立补偿。Redis Lua 使用 match_id 幂等，成功执行但回复丢失时重试不会重复加分。

在线恢复写入只有 COMMIT 成功后 ACK；提交回复丢失后匹配存储序号、owner 与完全相同 blob。full 保存完整状态，tail 保存周期快照及连续权威增量，二者完整恢复保证相同。

## 方案选择

批量检查点在跨房间共同事务中减少提交开销，同 COMMIT 后才确认成员请求。当前 batch 默认 16，范围 1–32；并发请求累计等待与物理事务耗时采用不同分母。

full/tail 对照固定配置、操作轨迹和采用门槛，分别测运行与恢复。tail 减少逻辑写入量，但主要规模收益不稳定，因此默认保留 full，tail 可配置；结果见 [策略报告](recovery-strategy-report.md)。

## 验证原则

单元验证规则和队列内核；协议验证私有状态、数值与兼容；集成验证事务/重启/精确故障窗口；sanitizer 检查内存与未定义行为；普通 Release 用于性能测量。各项提供不同证据，不能互相替代。

测试使用隔离 schema、随机身份和定向清理，保留正常服务与命名卷。强杀进程、提交回复丢失、DNS 延迟和控制台信号分别使用明确注入方法，不以任意终止或模拟结果替代真实边界。

演示入口、技术路径、公开样本与限制集中在 [文档导航](README.md)；源码和报告保持一致。
